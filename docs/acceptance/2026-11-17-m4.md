# Acceptance record — 2026-11-17 (M4)

Environment: a single-node-group Kubernetes cluster, one claim-based backend (namespace `<ns>`, CRD
coordinates supplied by configuration), pool size 2, lease `ttl` 420s / `grace` 60s for the long test
and 30s/10s for the reap test. The client identity is a **non-default** profile's own key; the default
identity was left on its previous path for the whole run.

All checks were run as real SSH sessions against the running binary; nothing was mocked.

## Bugs this run found (all fixed, all now covered by tests)

1. **Claim kind was derived from the resource name** — `sandboxclaims` → `Sandboxclaim`, rejected by the
   API server (`must be SandboxClaim`). Guessing capitalisation does not survive contact with a real
   CRD, so `provider.claim_kind` is now configuration.
2. **Pooled instances were never bound to an identity.** A warm instance handed to an identity carried
   no annotation, so a restart could not adopt it and left an orphan. Fix: `backend.Binder`;
   `Manager.Acquire` binds a pooled instance before returning it, and a failed bind returns the
   instance instead of leaking it.
3. **Stale warm capacity was never reaped.** Adoption now destroys managed instances without an
   identity annotation (they are the previous process's pool) and refills afterwards; adoption runs
   *before* warming, otherwise the warmer immediately creates more stale capacity.
4. **Readiness was "the status field exists".** The controller publishes `serviceFQDN` before the
   Service resolves; four of six concurrent sessions failed with `no such host`. Readiness is now a
   TCP connect to one of the advertised addresses (`serviceFQDN`, then `podIPs`), which is also immune
   to the fake-IP DNS this network returns for unknown names.
5. (from M1, still worth recording) `exit-status` was dropped when the target closed the channel
   before the queued request was flushed, and `ssh.DiscardRequests` blocks when called inline.
