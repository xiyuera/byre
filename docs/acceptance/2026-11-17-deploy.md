## Build

The build host had no container runtime for a `docker build` of the canonical multi-stage Dockerfile
(no base-image registry reachable), so the binary was built with `make build` and packaged with
`Dockerfile.prebuilt` (`FROM scratch`, pulls nothing):

```
podman build -f Dockerfile.prebuilt -t <registry>/keypod:v0.1.0 .
podman run --rm --network host keypod:v0.1.0 -version
v0.1.0-3-g2ed1b0c-dirty (2ed1b0c, 2026-11-17T01:29:40Z)
podman push --tls-verify=false <registry>/keypod:v0.1.0
sha256:b784456db93c16e512912512105de59fadf67f78803b9d93d099857a3d93bdd3
```

Image size 42 MB; the runtime is a single static binary with a passwd entry, non-root uid 10001.

## Deploy

`deploy/` is namespaced to the gateway, but instances are created in a *different* namespace, so the
Role/RoleBinding must live next to the instances and name the gateway's ServiceAccount as subject:

```yaml
subjects: [{kind: ServiceAccount, name: keypod, namespace: keypod-system}]
```

Objects created: Namespace, ServiceAccount, Role + RoleBinding (instance namespace), Secret (pool key),
ConfigMap, Deployment, Service.

## Two defects the deployment exposed

1. **`patch` was missing from the Role.** A pooled instance is bound to its identity by patching
   annotations, so every checkout failed with
   `cannot patch resource "sandboxclaims"`. `create`/`delete` are not enough.
2. **The Secret was unreadable to the container.** Mounted with `defaultMode: 0400` and owned by root,
   while the container runs as uid 10001: `open /etc/keypod/keys/id_key: permission denied`. Fixed with
   `fsGroup: <uid>` + `fsGroupChangePolicy: OnRootMismatch` on the pod security context.

Both are fixed in `deploy/rbac.yaml` and `deploy/deployment.yaml`.

```
== AC5: adoption
  INFO  leases adopted at startup: 1     # the pod had restarted between requests
== pool
  INFO  warm instances: 2
  passed=3 failed=0
```

A real session through the Service:

```
$ ssh -p 2222 -i <client-key> root@byre.byre-system.svc.cluster.local \
    'echo $(hostname) $(id -u)'
keypod-b171c9c2 0
```

That instance name is the same one the identity held before the Deployment rolled, so adoption works
across a pod restart in the deployed setting too.

## First install now owns its identity

The host key used to be supplied by hand (a Secret). Replacing that with a PVC plus generate-on-first-
start was verified as a first install would experience it:

```
empty PVC                 -> pod starts, logs "generated a new host key and persisted it",
                             fingerprint SHA256:coVWKmEdv8pCdJy/ut2OEMykQY83zFvpCz8QaKyxuTI
delete pod (1st)          -> same fingerprint
delete pod (2nd)          -> same fingerprint
five profiles,            -> ops eng legal research reviewer all connect
StrictHostKeyChecking=yes
```

Clients that had pinned the previous ephemeral fingerprint had to drop it once
(`ssh-keygen -R '[<host>]:<port>'`), which is also what a deliberate rotation requires — see ADR-0006.

## The gateway is disposable, the instances are not

A mistake turned into a useful experiment: the whole `keypod-system` namespace was deleted (Deployment,
Service, ConfigMap, Secret, ServiceAccount) and recreated from scratch, twice.

- The instances did **not** move: they are objects in the *instance* namespace, which the gateway only
  owns by label.
- After recreation the new process adopted the surviving lease (`keypod_leases_adopted 1`) and the same
  client identity landed on **the same sandbox** — the one it had been using before the namespace was
  removed.
- Nothing leaked: no second instance was created for that identity, and the pool was back to 2.

That is the property the design aims for — the gateway holds state that is rebuildable, and the state
that matters (which identity holds which instance) is written down in the cluster, not in the process.

## Resource note

With `pool_size: 2` the deployment keeps two warm instances alive at all times. Scale the Deployment to
0 (or set `pool_size: 0` in the ConfigMap) when the gateway is not needed; the leases are reaped by
their own `ttl` within minutes.
