# 为什么不是普通跳板机

跳板机把一条连接转发到目标。按**连接**分配 instance 看起来是同一件事，却在三处失效：

| 发生什么 | 客户端看到什么 | 实际坏在哪 |
|---|---|---|
| 第 2 条连接落在 instance B | 每条命令都成功 | 它上传的文件树在 A 上 |
| lease 在两条命令之间过期 | `cd: no such file or directory` | instance 在任务中途被回收 |
| 两个 agent 共用一把密钥 | 一个看到另一个的文件 | 问题在密钥分发，不在网关 |

**中间那种最贵**，因为每条命令都成功。客户端的账本描述着*一个*文件系统，而网关悄悄给了它三个。这里没有错误可捕：故障之后才冒出来，表现为构建里少了一个文件，或者一个本地能过、这里过不了的测试。

修法是把分配绑在一个比连接活得久的标识上。认证之后，SSH 恰好只携带一样这样的东西——客户端证明自己持有的那把公钥。这就是 identity，lease 挂在它上面。没有要传的 token，没有要记的标识符，没有要保活的 `ControlMaster`。

## 四种看起来显然的修法

每一种都像是能在不改模型的前提下解决问题，每一种都因不同原因失败。

**按源地址分配。** 地址标识的是网络，不是客户端。NAT 后面同一台笔记本上的每个 agent 共用它，于是两个 agent 变成一个 identity；NAT 还可能在空闲之后重编号端口映射，于是在 t+0s 能标识客户端的那条地址，在 t+5min 谁也标识不了。从地址判断「是不是同一个客户端」，等于在猜一个由客户端所在网络改写的东西。

**按 SSH session 分配。** 根本没有可依托的 session：session 标识由承载它的连接创建。网关终结 SSH，所以它能观察到的唯一 session 就是它刚创建的那个——恰好是断开时被销毁的对象。重连、`scp`、每一条 `-L` 转发，按协议设计都是带新 session 的新连接。

**连接断开就销毁 instance。** 这是自洽的做法——instance 的生命周期就是连接的生命周期——但它让状态在连接之间无处安放，而那正是整个问题所在。它适合交互式 shell，不适合由一串连接构成的任务。

**要求客户端保持一条连接不关（`ControlMaster`）。** 这在 `ControlPersist` 过期之前有效，而那次过期恰好就是设计必须扛住的那次重连。它还把正确性变成了客户端配置：任何不这么做的客户端，或者像参考客户端那样为 `scp` 开一条普通 socket 的客户端，都会静默坏掉。

完整论证，包括按公钥分配所付出的代价，在[架构](handbook/architecture.md#7-why-the-obvious-alternatives-do-not-work)里。
